## 1. 项目概述

### 1.1 项目背景

校园宿舍日常维修存在三个痛点：报修靠电话/微信群，信息零散不落库；维修工靠人工口头派活，忙闲不均、责任不清；管理员无数据支撑，无法量化维修效率与返修情况。本系统将"报修—派单—上门—完工—评价—统计"全流程线上化、可追溯。

### 1.2 建设目标

| 目标      | 可量化指标                             |
| ------- | --------------------------------- |
| 报修流程线上化 | 学生报修 100% 落库，含照片证据                |
| 派单可调度   | 支持管理员按楼栋派单 + 维修工抢单两种模式            |
| 过程可追踪   | 工单全流程 9 个状态（8 个流转态 + 已取消）、维修轮次与流转轨迹全留存 |
| 时效可考核   | 自动/手动标记超时工单，超时率可统计                |
| 数据可视化   | 故障类型分布、平均处理时长、返修率三项指标可视化          |

### 1.3 角色与职责

| 角色    | 代码         | 核心职责                                 |
| ----- | ---------- | ------------------------------------ |
| 学生    | `STUDENT`  | 提交报修单（楼栋/房间/故障类型/照片/描述）、查看进度、确认完工并评价 |
| 维修人员  | `REPAIRER` | 接单/抢单、登记到场时间、填写维修过程与更换配件、提交完工并上传完工照片 |
| 宿舍管理员 | `MANAGER`  | 按楼栋区域派单、调整优先级、跟踪状态、标记超时、查看统计报表       |

### 1.4 功能清单（需求 → 功能点映射）

| 需求编号 | 角色  | 需求描述                | 对应功能点                                  |
| ---- | --- | ------------------- | -------------------------------------- |
| S-01 | 学生  | 提交报修单               | 选楼栋→房间→故障类型→上传现场照片(1\~6张)→填描述→提交，生成工单号 |
| S-02 | 学生  | 查看处理进度              | 工单列表 + 工单详情时间轴（状态流转记录）                 |

### 1.5 非功能需求

| 类别   | 要求                                                  |
| ---- | --------------------------------------------------- |
| 并发   | 支持 200 学生同时报修、20 维修工同时抢单不超卖（同一工单仅一人抢到）              |
| 响应时间 | 列表接口 P95 < 500ms；统计接口 P95 < 2s（走 Redis 缓存后 < 500ms） |
| 数据量  | 预估 5000 工单/学期，单表 5 万级，MySQL 单表可承载，预留分页与索引           |
| 可用性  | **轨迹与操作日志**（MongoDB）故障时可降级：详情时间轴回退为"工单表时间字段 + 派单/维修记录"拼装，日志仅丢失不影响主流程。**图片依赖 GridFS，属硬依赖**：MongoDB 不可用时上传接口返回 503，前端提示"图片服务暂不可用，请稍后再试"；报修提交本身在图片已上传成功的前提下不受影响（这是本方案的已知限制，不做本地图片兜底） |
| 安全   | JWT 鉴权 + 角色权限 + 接口级越权校验；密码 BCrypt；上传文件类型白名单         |
| 可维护性 | 四层架构（Controller/Biz/Service/Mapper）、统一响应体、统一异常处理、统一枚举字典          |

### 2.3 分层架构

```
┌─────────────────────────────────────────────┐
│  Nginx (80)：静态资源 / api 反代 / 图片       │
└─────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────┐
│  Controller 层（SpringMVC）                   │
│  参数校验 @Valid / 统一响应 R<T> / 全局异常    │
├─────────────────────────────────────────────┤
│  Biz 层（业务编排 + @Transactional）           │
│  状态机流转 / 派单抢单 / 跨 Service 组合       │
├─────────────────────────────────────────────┤
│  Service 层（原子操作，不跨模块编排）           │
│  单表读写 / 缓存读写 / 轨迹写入 / 号段生成      │
├─────────────────────────────────────────────┤
│  Mapper 层（MyBatis-Plus BaseMapper + XML）    │
└─────────────────────────────────────────────┘
      ↓                ↓                ↓
   MySQL            Redis            MongoDB
 (业务主数据)    (缓存/锁/统计)   (轨迹/日志/图片)
```

**分层职责边界（照做即可，别再加层）**

| 层                    | 允许做的事                                         | 禁止做的事                                                |
| -------------------- | --------------------------------------------- | ---------------------------------------------------- |
| Controller           | 接参、`@Valid` 校验、调用**一个** Biz 方法、返回 `R<T>`      | 写业务判断、直接调 Service/Mapper、拼装多表查询、`try/catch` 业务异常    |
| Biz（业务编排）          | 事务边界、状态机流转、并发控制、跨模块编排（"派单 + 发通知 + 写轨迹"）、组合多个 Service | 出现 `HttpServletRequest`/`Response`、返回 `R` 包装、直接拼 SQL、只做一行纯转发 |
| Service（原子服务）       | 单表 CRUD、缓存读写、轨迹/日志写入、工单号生成；可被多个 Biz 复用        | 开启跨模块事务编排、调用别的 Biz、拼装多表业务判断                       |
| Mapper               | 单表 CRUD 与聚合查询（XML 写复杂统计 SQL）                  | 写业务分支、调用其他 Mapper（跨表联查放 Biz 编排或单条 SQL join）        |
| Converter（MapStruct） | Entity ↔ VO/DTO                               | 查库、调外部服务                                             |

> 参照项目 heritage-craft-backend 同时存在 `biz` 与 `service` 两套同名接口：`CraftBiz.listCrafts()` 与 `CraftService.listEnabledCrafts()` 几乎重复，`AnnouncementBizImpl`/`UserBizImpl`/`NotificationBizImpl` 只有 28\~29 行纯转发。**本项目保留 Biz 层（与 AGENTS.md 一致），但禁止纯转发**：Biz 必须承担事务边界或多 Service 组合，否则直接由 Controller 调 Service，见 3.3 铁律 ①。

### 2.4 关键设计决策（必须在编码时遵守）

| 编号   | 决策                                                                                                                                                | 理由                                                                   |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| D-01 | 工单状态一律用 `varchar` 枚举字符串存（`CREATED`/`ASSIGNED`…），不用数字                                                                                              | 可读性、便于排查、避免魔法值；字典集中在 `OrderStatusEnum`                               |
| D-02 | 图片二进制存 MongoDB GridFS，MySQL 只存 `file_id`                                                                                                          | 避免 MySQL 大字段膨胀，符合"必须使用 MongoDB"的技术栈要求，且天然支持按 fileId 直接流式返回           |
| D-03 | 抢单必须走 Redis `SETNX + TTL` 分布式锁，且数据库层用 `UPDATE ... WHERE status='CREATED' AND assignee_id IS NULL` 的 CAS 兜底 | 单机锁不可靠；并发抢单必须只有一个成功                                                  |
| D-04 | 学生提交报修做幂等（Redis 30 秒内同用户同房间同故障类型拦截）                                                                                                               | 防抖动重复提交，避免重复工单                                                       |
| D-05 | 超时判定以"计划时间"字段为准，由定时任务扫描 + 管理员手动标记双通道                                                                                                              | 自动为主、人工纠偏为辅                                                          |
| D-06 | 统计接口优先读 Redis 缓存（TTL 5\~10 分钟），并提供强制刷新接口                                                                                                          | 统计聚合 SQL 较重，避免拖慢主流程                                                  |
| D-07 | 所有时间字段统一 `datetime`，服务器时区 `Asia/Shanghai`                                                                                                         | 避免时区混乱；接口返回 `yyyy-MM-dd HH:mm:ss`                                    |
| D-08 | 前端三端共用一个工程，按路由 + 角色动态菜单隔离                                                                                                                         | 降低维护成本；`/student`、`/repairer`、`/admin` 前缀区分                          |
| D-09 | **模块化分包**：`module/{order,evaluation,stat,file,user,auth,basedata,notice}`，每个模块内部自带 `controller/biz/service/mapper/entity/dto`；顶层只留 `common`/`config`/`infra` | 改一个业务只动一个目录；避免"顶层 entity 堆 26 个类、controller 堆 13 个类"的平铺结构（参照项目现状）    |
| D-10 | **一个角色一个 Controller**：`OrderStudentController` / `OrderRepairerController` / `OrderManagerController`，共享 `OrderService`                           | 权限注解与入参校验天然按角色归位，单文件不超 200 行；避免 3 个角色挤在一个 `OrderController` 里靠 if 判断 |
| D-11 | **保留 Biz 编排层但禁止纯转发**：Biz 只做多 Service 组合、事务边界与状态机流转；Service 只做原子操作 | 与 AGENTS.md 的分层一致；避免参照项目"10 个 BizImpl 里 6 个是纯转发、改一个方法要改 3 处"的负担 |
| D-12 | 统一用 Spring Security + `@PreAuthorize` 做角色控制，Filter 校验 JWT；**不再自建 AuthInterceptor**                                                                | 与参照项目一致，减少一套自研鉴权代码；`@PreAuthorize("hasRole('MANAGER')")` 比手写拦截器易维护   |
| D-13 | 所有业务表实体继承 `BaseEntity`（`createTime`/`updateTime`/`deleted`），由 `MetaObjectHandler` 自动填充；**`version` 只放在并发写的表**（`t_work_order`、`t_repair_record`） | 避免每个 Service 手动 `setCreateTime`；字典表不加 `version`，避免无意义字段与 DDL/实体不一致           |
| D-14 | 关键操作（派单、调优先级、标记超时、删除）必须用 `@OpLog(module=..., action=...)` AOP 注解记录到 MongoDB                                                                       | 审计与排查需求；参照项目已有该模式，直接复用                                               |

**为什么模块内自带 entity/mapper**（对照参照项目）：heritage-craft-backend 采用"顶层 `entity/`(26 个) + `mapper/`(23 个) + `dto/`(39 个) 平铺"，结果一个"工艺档案"改动要在 5 个顶层目录之间来回跳；本系统改为模块内自洽后，改"派单"只进 `module/order` 一个目录。若担心跨模块复用实体，通过 `Service` 接口引用，不要引用别模块的 `entity`；**别模块的 `Biz` 一律不可注入**（Biz 是模块内的用例入口，不是可复用能力）。

**为什么不是每个模块都有 biz**：`user`/`basedata`/`stat`/`file` 的用例都是"单表操作 + 一次查询"，加了 Biz 只会变成纯转发（违反铁律 ①）。只有 `auth`/`order`/`evaluation`/`notice` 需要事务边界或多 Service 组合，才建 Biz。

### 3.3 分层铁律（违反即返工）

| 编号 | 铁律                                                                    | 反例（参照项目里真实存在的写法）                                                               |
| -- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| ①  | **Biz 只做编排、Service 只做原子操作；禁止 `Biz` 里只有一行纯转发**                      | `CraftBizImpl.listCrafts()` 里只有 `return craftService.listEnabledCrafts();`，纯转发 |
| ②  | Controller 不出现 `if (role == ...)` 判断权限，权限交给 `@PreAuthorize`           | 单 Controller 内按 `CurrentUser` 判断角色后走不同分支                                       |
| ③  | 状态变更只能走 `OrderStateMachine.transit(...)`，禁止 `updateById` 直接改 `status` | —                                                                              |
| ④  | 跨模块调用只依赖对方 `Service` 接口，禁止注入对方 `Mapper`                               | —                                                                              |
| ⑤  | `config` 包不允许出现 `@Transactional` 与查库逻辑                                | `NotificationMigrationRunner` 这类启动迁移代码应放 `infra/` 或 `job/`                     |
| ⑥  | 实体只映射表字段，VO/DTO 才承载展示字段；转换统一用 MapStruct                               | 在 Controller 里手写 `vo.setXxx(entity.getXxx())` 十几个字段                            |
| ⑦  | Controller 只调本模块 `Biz`；跨模块只依赖对方 `Service`，禁止注入对方 `Biz`/`Mapper`         | 在 `order` 模块里直接注入 `user` 模块的 `SysUserMapper`                                     |

### 3.4 命名规范

| 类型         | 规则                                      | 示例                                    |
| ---------- | --------------------------------------- | ------------------------------------- |
| Controller | `{领域}{角色}Controller`                    | `OrderManagerController`              |
| Biz        | `{领域}Biz` + `impl/{领域}BizImpl`          | `DispatchBiz` / `DispatchBizImpl`     |
| Service    | `{领域}Service` + `impl/{领域}ServiceImpl`  | `DispatchServiceImpl`                 |
| Mapper     | `{实体}Mapper`（与实体同名）                     | `WorkOrderMapper`                     |
| 实体         | 单数、驼峰、与表名对应（去掉 `t_`）                    | `t_work_order` → `WorkOrder`          |
| 请求对象       | `{动作}Request`                           | `OrderCreateRequest`                  |
| 响应对象       | `{场景}VO`                                | `OrderDetailVO`、`TypeDistVO`          |
| 枚举         | `{领域}Enum`，值全大写下划线                      | `OrderStatusEnum.ASSIGNED`            |
| Redis Key  | `sr:{模块}:{业务}:{标识}`，集中在 `RedisKeys` 常量类 | `RedisKeys.ORDER_GRAB_LOCK + orderId` |
| 前端视图       | `{模块}{动作}View.vue`                      | `OrderCreateView.vue`                 |
| 前端 store   | `use{模块}Store`                          | `useUserStore`                        |
| 接口函数       | `{动词}{名词}`，与后端路径同序                      | `grabeOrder` → `grabOrder(id)`        |

### 4.4 关键冗余字段说明

`t_work_order` 冗余了 `building_id`、`room_no`、`fault_type_name`、`fault_category`，目的：

1. 按楼栋/大类统计不需要 join 房间表与故障类型表；
2. 房间/故障类型后续被改名、停用或删除时，历史工单仍能正确展示与统计当时的信息（快照语义）；
3. 减少统计 SQL 的 join 层数，保证 P95 性能。

> 注意：`t_work_order` 里**不再冗余 `arrive_time` 之外的维修过程字段**。维修到场时间只在工单表保存一份，`t_repair_record` 不再重复存 `arrive_time`，避免两处不一致；维修耗时 `cost_minutes` 由 `finish_time - t_work_order.arrive_time` 计算后写入 `t_repair_record.cost_minutes`。

### 5.2 抢单并发控制（必须实现的完整逻辑）

```java
// DispatchBiz.grabOrder(Long orderId)
// Controller 从 SecurityContext 取 repairerId，禁止前端传入（否则可替他人抢单）
@Transactional(rollbackFor = Exception.class)
public void grabOrder(Long orderId) {
    Long repairerId = SecurityUtils.getCurrentUserId();
    // 0. 资格校验：角色 REPAIRER、账号启用、工单楼栋在其负责范围内
    repairerService.assertCanGrab(repairerId, orderId);
    String lockKey = RedisKeys.ORDER_GRAB_LOCK + orderId;
    String requestId = UUID.randomUUID().toString();
    // 1. 加锁：SETNX + TTL 10s
    Boolean locked = redisTemplate.opsForValue()
            .setIfAbsent(lockKey, requestId, 10, TimeUnit.SECONDS);
    if (!Boolean.TRUE.equals(locked)) {
        throw new BizException(ResultCode.ORDER_ALREADY_TAKEN); // 409
    }
    try {
        // 2. 数据库条件更新：抢单即接单，一步进入 ACCEPTED（写 accept_time）
        int rows = dispatchService.grabUpdate(orderId, repairerId);
        if (rows == 0) {
            throw new BizException(ResultCode.ORDER_ALREADY_TAKEN);
        }
        // 3. 同事务内：派单记录 + 轨迹
        dispatchService.saveGrab(orderId, repairerId);
        orderTrackService.record(orderId, "CREATED", "ACCEPTED", repairerId, "REPAIRER", "抢单成功（视为接单）");
    } finally {
        // 4. 释放锁（Lua 比对 requestId，防误删他人锁）
        redisTemplate.execute(UNLOCK_LUA, Collections.singletonList(lockKey), requestId);
    }
    // 5. 事务提交后再删缓存/发通知，避免回滚造成脏缓存与误通知
    cacheEvict(orderId);
    noticeService.pushGrabbed(orderId, repairerId);
}
```

对应 Mapper SQL（`DispatchMapper.xml`）：

```xml
<update id="grabUpdate">
  UPDATE t_work_order
     SET status = 'ACCEPTED',          <!-- 抢单即接单，不再经过 ASSIGNED -->
         assignee_id = #{repairerId},
         dispatch_type = 'GRAB',
         assign_time = NOW(),
         accept_time = NOW(),
         version = version + 1
   WHERE id = #{orderId}
     AND deleted = 0
     AND assignee_id IS NULL
     AND status = 'CREATED'            <!-- 只有待抢池可抢；ASSIGNED 是已派给指定人，不允许他人抢 -->
</update>
```

> 两条路径的差异：**管理员派单** = `CREATED → ASSIGNED`，维修工再"接单"→ `ACCEPTED`；**抢单** = `CREATED → ACCEPTED` 一步到位。两者最终状态一致，避免"抢完还要再接一次"的冗余操作与接单超时误判。

解锁 Lua（`RedisScript`）：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end
```

> **双重保障说明**：Redis 锁解决"同一瞬间并发"，`UPDATE ... WHERE assignee_id IS NULL` 解决"锁失效后仍只有一个成功"。二者必须同时存在，缺一不可（测试用例 TC-R-01 专门验证）。

### 5.3 超时扫描机制

- **单一截止时间**：每个工单只有一个 `deadline_time = create_time + expect_hours`（BR-10），不设"接单/到场/完工"分环节 SLA，避免出现多个互相冲突的时限。
- 创建工单时：`ZADD sr:order:timeout:zset score=deadlineTime(epochSecond) member=orderId`，并 `EXPIRE` 30 天兜底（ZSet 无法按成员过期；工单最长时限 72h，30 天足够）。
- 调整优先级/期望时长时：先 `ZREM` 再 `ZADD` 更新 score。
- 定时任务（每 5 分钟，`@Scheduled(cron = "0 */5 * * * ?")`）：
  1. `ZRANGEBYSCORE sr:order:timeout:zset 0 now LIMIT 0 200` 取到期工单
  2. 逐条判断：若工单仍处于未终结状态（CREATED/ASSIGNED/ACCEPTED/ARRIVED）→ 标记 `timeout_flag=1`，按**当前所处状态**决定 `timeout_type`（CREATED/ASSIGNED→ACCEPT，ACCEPTED→ARRIVE，ARRIVED→FINISH），写 `t_timeout_record(mark_type='AUTO')`；`uk_order_type` 保证同一环节只记一条，工单表的 `timeout_type` 只保留最近一次超时环节
  3. `ZREM` 该 member，并推送管理员超时通知
- 工单进入 CONFIRMED/CLOSED/CANCELLED 时：`ZREM`（终态不再参与超时判定）
- 状态推进（如 ACCEPTED→ARRIVED）**不重算 deadline、不重新入队**：deadline 只由创建与管理员调优先级决定
- 管理员手动标记：直接写 `t_timeout_record(mark_type='MANUAL', mark_by=管理员id)`，并置 `timeout_flag=1`，同时 `ZREM`（避免自动任务重复写）；已标记过的环节再点，返回幂等成功

3. 单文件 ≤ 5MB；`BEFORE`/`AFTER` 各 ≤6 张，单工单总量 ≤12 张（BR-13）
4. 用 `ImageIO.read()` 实际解码校验，防改后缀的伪造文件
5. 文件名重命名：`UUID + 后缀`，防路径穿越与中文乱码

下载/预览：`GET /api/v1/files/{fileId}` → `gridFsTemplate.getResource(fileId)`，设置 `Content-Type` 与 `Cache-Control: max-age=86400`，直接流式写出。Nginx 侧用 `proxy_pass` 转发该路径（不落本地磁盘）。

## 7. 工单状态机与核心业务规则

### 7.1 状态定义（9 个状态，已删除 v1.0 的 `REJECTED`）

| 状态          | 名称      | 进入条件                         | 允许的下一状态                                 |
| ----------- | ------- | ---------------------------- | --------------------------------------- |
| `CREATED`   | 待派单/待抢单 | 学生提交成功 或 拒单/弃单释放后回到此状态        | `ASSIGNED`（管理员派单）、`ACCEPTED`（维修工抢单直达）、`CANCELLED` |
| `ASSIGNED`  | 已派单/待接单 | 管理员派单                        | `ACCEPTED`（维修工接单）、`CREATED`（拒单/撤回）、`CANCELLED` |
| `ACCEPTED`  | 已接单/待上门 | 维修工接单 或 抢单成功                 | `ARRIVED`、`CREATED`（管理员确认弃单，见 BR-15）       |
| `ARRIVED`   | 已到场/维修中 | 维修工登记到场时间                    | `FINISHED`                              |
| `FINISHED`  | 本轮完工/待验收 | 维修工提交完工（含维修后照片）              | `CONFIRMED`（学生验收通过）、`REWORKING`（学生判定未完成） |
| `REWORKING` | 返修中     | 学生对 `FINISHED`/`CLOSED` 工单发起返修（原因必填） | `ARRIVED`（维修工到场）、`CREATED`（管理员释放，仅管理员）、`CANCELLED` |
| `CONFIRMED` | 已确认/待评价 | 学生确认 或 系统自动确认            | `CLOSED`（已评价 或 评价窗口满）              |
| `CLOSED`    | 已完成     | 已评价 或 CONFIRMED 满期限未评价     | `REWORKING`（售后返修）                       |
| `CANCELLED` | 已取消     | 学生取消（仅 CREATED/ASSIGNED 可取消） | —（终态）                                   |

> **返修不再新建工单**：学生判定未完成时原工单直接 `FINISHED/CLOSED → REWORKING`，`current_round + 1`，同一 `orderId` 继续流转；每轮维修/验收分别写入 `t_repair_round`、`t_order_acceptance`，历史轮次只读。

> **两种接单路径**：管理员派单走 `CREATED → ASSIGNED → ACCEPTED`；维修工抢单走 `CREATED → ACCEPTED`（抢单即接单，不再多一步）。`ASSIGNED` 是"派给指定人、等其确认"，因此不允许被其他人抢。

> **为什么删掉** **`REJECTED`**：一个工单只有一个 `status`，若拒单把状态改成 `REJECTED` 再接 `REJECTED→ASSIGNED`，就会出现"工单此刻既在派单池、又挂着拒单状态"的语义冲突，且看板会多出一列永远为空的"已拒单"。改为：**拒单不改 status，回到** **`CREATED`** **并清空** **`assignee_id`**，拒单这件事由 `t_dispatch_record(dispatch_type='REJECT')` 记录，天然可统计"谁拒过几次"。

### 7.3 状态机实现（`OrderStateMachine.java`，编码必须用此模式）

```java
@Getter
public enum OrderStatusEnum {
    CREATED("待派单"), ASSIGNED("待接单"), ACCEPTED("待上门"), ARRIVED("维修中"),
    FINISHED("待确认"), REWORKING("返修中"), CONFIRMED("待评价"), CLOSED("已完成"), CANCELLED("已取消");

    private final String label;
    OrderStatusEnum(String label) { this.label = label; }

    private static final Map<OrderStatusEnum, Set<OrderStatusEnum>> ALLOWED = new EnumMap<>(OrderStatusEnum.class);
    static {
        ALLOWED.put(CREATED,   EnumSet.of(ASSIGNED, ACCEPTED, CANCELLED)); // ACCEPTED = 抢单直达
        ALLOWED.put(ASSIGNED,  EnumSet.of(ACCEPTED, CREATED, CANCELLED));  // CREATED = 拒单/撤回
        ALLOWED.put(ACCEPTED,  EnumSet.of(ARRIVED, CREATED));              // CREATED = 管理员确认弃单
        ALLOWED.put(ARRIVED,   EnumSet.of(FINISHED));
        ALLOWED.put(FINISHED,  EnumSet.of(CONFIRMED, REWORKING));          // REWORKING = 学生判定未完成
        ALLOWED.put(REWORKING, EnumSet.of(ARRIVED, CREATED, CANCELLED));   // CREATED = 管理员释放
        ALLOWED.put(CONFIRMED, EnumSet.of(CLOSED));
        ALLOWED.put(CLOSED,    EnumSet.of(REWORKING));                     // 售后返修
        ALLOWED.put(CANCELLED, EnumSet.noneOf(OrderStatusEnum.class));
    }

    public boolean canTransitTo(OrderStatusEnum target) {
        return ALLOWED.get(this).contains(target);
    }
    public boolean isTerminal() { return this == CLOSED || this == CANCELLED; }
}

/** 唯一流转入口：任何 status 变更都必须走这里，禁止 service 里 updateById 改 status */
public void transit(Long orderId, OrderStatusEnum target, Long operatorId, String role,
                    String remark, Map<String, Object> extraFields) {
    WorkOrder order = orderMapper.selectById(orderId);
    if (order == null) throw new BizException(ResultCode.ORDER_NOT_FOUND);
    OrderStatusEnum current = OrderStatusEnum.valueOf(order.getStatus());
    if (!current.canTransitTo(target)) {
        throw new BizException(ResultCode.ILLEGAL_STATUS_TRANSIT);
    }
    // 弃单只能由管理员确认，维修工不得自行 ACCEPTED→CREATED
    if (current == ACCEPTED && target == CREATED && !"MANAGER".equals(role)) {
        throw new BizException(ResultCode.FORBIDDEN);
    }
    // 1) 条件更新：WHERE id=? AND status=当前状态（并发下影响 0 行即失败）
    int rows = orderMapper.transitUpdate(orderId, current.name(), target.name(), extraFields);
    if (rows == 0) throw new BizException(ResultCode.CONCURRENT_MODIFIED);
    // 2) 时间字段由 7.5 规则在 extraFields 中带入，禁止前端传
    // 3) 轨迹（MongoDB）+ 通知（WebSocket）+ 缓存清理
    orderTrackService.record(orderId, current.name(), target.name(), operatorId, role, remark);
    cacheService.evictOrder(orderId);
    noticeService.pushStatusChanged(orderId, target);
    // 4) 终态移除超时 ZSet；非终态保持原 deadline，仅校正 score（不重算、不重复入队）
    timeoutQueueService.sync(orderId, target);
}

/** 拒单：不是"状态流转"，而是"释放派单"——回到 CREATED 并清空 assignee。仅限 ASSIGNED（尚未接单） */
public void reject(Long orderId, Long repairerId, String reason) {
    WorkOrder order = orderMapper.selectById(orderId);
    if (order == null || !repairerId.equals(order.getAssigneeId())) {
        throw new BizException(ResultCode.FORBIDDEN);
    }
    if (OrderStatusEnum.valueOf(order.getStatus()) != OrderStatusEnum.ASSIGNED) {
        // 已接单（ACCEPTED）不允许自助拒单，必须走 release 由管理员确认
        throw new BizException(ResultCode.STATUS_NOT_ALLOWED);
    }
    dispatchService.clearAssignee(orderId);                          // 先清空 assignee 再流转，避免 transit 内 pushStatusChanged 读到旧 assignee
    transit(orderId, OrderStatusEnum.CREATED, repairerId, "REPAIRER", "拒单：" + reason, Map.of());
    dispatchService.saveReject(orderId, repairerId, reason);         // 留痕，供"同一人拒 2 次不再推送"判断
    noticeService.pushToManager(orderId, "维修工拒单，请重新派单");
}

/** 管理员确认弃单：ACCEPTED → CREATED，必须先校验其对该楼栋有管理权限 */
public void release(Long orderId, Long managerId, String reason) {
    WorkOrder order = orderMapper.selectById(orderId);
    if (order == null) throw new BizException(ResultCode.ORDER_NOT_FOUND);
    buildingService.assertCanManage(managerId, order.getBuildingId());
    if (OrderStatusEnum.valueOf(order.getStatus()) != OrderStatusEnum.ACCEPTED) {
        throw new BizException(ResultCode.STATUS_NOT_ALLOWED);
    }
    dispatchService.clearAssignee(orderId);                          // 先清空 assignee 再流转，理由同 reject
    transit(orderId, OrderStatusEnum.CREATED, managerId, "MANAGER", "管理员确认弃单：" + reason, Map.of());
    dispatchService.saveRelease(orderId, managerId, reason);         // dispatch_type='RELEASE'
}
```

> 注意：`transit` 的 `extraFields` 不要用 `Map.of("assignee_id", null, ...)`——`Map.of` 禁止 null 值，运行期会 NPE。清空字段统一走 `dispatchService.clearAssignee()` 的专用 SQL，语义更明确。

> `transitUpdate` 的 SQL 必须是 `UPDATE t_work_order SET status=#{target}, ... WHERE id=#{id} AND status=#{current} AND deleted=0`，用状态做 CAS，而不是靠 `version` 字段单独判断（两者并存更稳）。

### 7.4 场景规则明细（每个都必须有测试用例）

| 规则编号  | 场景      | 规则                                                                                                                                                                                                                              |
| ----- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| BR-01 | 学生取消    | 仅 `CREATED`/`ASSIGNED` 可取消；`ACCEPTED` 及以后需联系管理员，学生端按钮置灰并提示                                                                                                                         |
| BR-02 | 维修工拒单   | **仅 `ASSIGNED`（尚未接单）可拒**；拒单不改状态值，统一回到 `CREATED` 并清空 `assignee_id`/`assign_time`/`dispatch_type`，写 `t_dispatch_record(dispatch_type='REJECT')` 留痕，通知管理员重新派单。同一维修工对同一工单累计拒单 **2 次**后，该单不再出现在其抢单池/派单推荐中。已接单后的放弃见 BR-15 |
| BR-03 | 抢单范围    | 维修工只能看到自己负责楼栋/区域（`t_user.building_id`）内的 `CREATED` 工单；管理员派单可跨楼栋但需二次确认提示；`ASSIGNED` 的工单只对指定维修工可见，其他人不可抢 |
| BR-04 | 到场登记    | `arrive_time` 由服务端 `NOW()` 写入，**忽略前端传入的时间**（防造假）；由于不接收前端时间，"到场早于接单"在正常链路不可能出现，仅在历史数据导入/修复脚本中做校验 |
| BR-05 | 配件明细    | 每次提交维修记录时整单覆盖（先删后插），避免多次提交产生重复配件行                                                                                                                             |
| BR-06 | 完工前置    | 提交完工必须：已到场 + 维修过程非空（≥10 字）+ 至少 1 张完工照片（`AFTER`）+ （至少 1 条配件 或 `t_repair_record.no_parts_flag=1`）                                    |
| BR-07 | 返修      | 学生点"未修好"→ **原单状态直接进入 `REWORKING`**（`FINISHED/CLOSED → REWORKING`），`current_round + 1`，原因必填；写 `t_order_acceptance(round_no, result='REJECT', reason)` 与新一轮 `t_repair_round`；默认仍派给原维修工，管理员可在返修中改派；**不新建工单**，全链路沿用同一 `order_id` 与 `root_order_id` |
| BR-08 | 评价唯一    | 每单只能评价一次（`uk_order` 兜底），评价后工单 `evaluate_flag=1` 并 `CONFIRMED→CLOSED`                                                                                                                |
| BR-09 | 优先级调整   | 管理员可调 P1\~P4；调整后重算 `deadline_time = create_time + expect_hours`，并更新 Redis ZSet score；写 `t_dispatch_record(CHANGE_PRIORITY)` 留痕；仅对非终态工单生效，已 `ARRIVED` 的工单不再重算 |
| BR-10 | 优先级对应时长 | P1(紧急)=4h、P2(高)=8h、P3(普通)=24h、P4(低)=72h；工单的 `expect_hours = min(优先级映射时长, 故障类型 expect_hours)`                                                                                     |
| BR-11 | 自动确认/自动关闭 | `FINISHED` 满 7 天未确认 → 定时任务自动置 `CONFIRMED`（视为默认认可）；`CONFIRMED` 满 7 天仍未评价 → 自动置 `CLOSED`。**评价窗口 = 进入 `CONFIRMED` 后的 7 天**，窗口内可评价，满窗自动关闭 |
| BR-12 | 权限      | 学生只能操作自己的工单；维修工只能操作 `assignee_id = 自己` 的工单；管理员只能操作 `t_manager_building` 中授权楼栋的工单（越权返回 403）                                                                                       |
| BR-13 | 图片数量    | 报修照片（`BEFORE`）1\~6 张、完工照片（`AFTER`）1\~6 张，**单工单总量 ≤12 张**；超出前端拦截 + 后端校验                                                                                                        |
| BR-14 | 工单号     | `WR + yyyyMMdd + 6位当日序列`，用 Redis `INCR sr:order:no:{yyyyMMdd}`（TTL 48h）生成，日切自动归零；Redis 不可用时退化为"按 uk_order_no 冲突重试 3 次" |
| BR-15 | 接单后弃单   | 维修工在 `ACCEPTED` 后要放弃，必须由**管理员在前端确认**后调用 `PUT /manager/orders/{id}/release` 执行 `ACCEPTED→CREATED`；禁止维修工自助退单。写 `t_dispatch_record(dispatch_type='RELEASE')` 时 `operator_id`=确认的管理员、`assignee_id`=被释放的维修工，据此把该次弃单计入该维修工拒单次数，影响后续派单排序 |
| BR-16 | 重复操作幂等  | 同一操作重复提交（连点两次"到场"/"确认"）必须幂等：服务端判断"当前状态已是目标状态"时直接返回上次结果（200 + 已有时间），**不报错、不覆盖首次时间、不重复写轨迹**                                        |
| BR-17 | 优先级来源   | **学生不能自选优先级**：提交报修时忽略前端 `priority`，由服务端取 `t_fault_type.default_priority` 计算；只有管理员可通过 BR-09 调整 |

### 7.5 时间字段填充规则

### 7.6 关键派生指标计算口径（**测试与统计必须一致**）

| 指标         | 公式                                                                                                | 说明                                |
| ---------- | ------------------------------------------------------------------------------------------------- | --------------------------------- |
| 响应时长       | `accept_time - create_time`（分钟）                                                                   | 抢单即时，派单看维修工反应                     |
| 到场时长       | `arrive_time - accept_time`（分钟）                                                                   | 考核上门速度                            |
| 维修时长       | `finish_time - arrive_time`（分钟）                                                                   | 写入 `t_repair_record.cost_minutes` |
| **平均处理时长** | `AVG(TIMESTAMPDIFF(MINUTE, create_time, finish_time))`，筛选 `status IN ('CONFIRMED','CLOSED')` 且 `finish_time ∈ [begin, end)` | 单位分钟，前端转"X小时Y分"                   |
| **返修率**    | 分子＝区间内 `t_order_acceptance.result='REJECT'` 的去重根单数；分母＝区间内完工（`CONFIRMED/CLOSED` 且 `id = root_order_id`）的根单数 × 100% | 同一根单最多计一次；分母为 0 返回 0，前端显示"—"；返修轮次不重复计入工单总数 |
| **报修类型分布** | `GROUP BY fault_category` 计数，区间内 `deleted=0` 全状态工单（按 `create_time ∈ [begin, end)`） | 直接用冗余快照，不再 join `t_fault_type` |
| 超时率        | `timeout_flag=1 的工单数 / 区间内创建工单数` × 100%（按 `create_time` 口径）                                                             | 辅助指标                              |

### 8.3 统计 SQL 参考（`src/main/resources/mapper/stat/StatMapper.xml`）

> 入参统一为 `StatQuery`：`LocalDateTime beginTime`、`LocalDateTime endTime`、`Long buildingId`。
> Controller 把前端 `2026-11-01 ~ 2026-11-17` 转成 **左闭右开**：`beginTime = 11-01 00:00:00`，`endTime = 11-18 00:00:00`（**次日零点**，不是 23:59:59），避免漏掉当天最后一秒的工单。
> 用 `LocalDateTime` 而非字符串传参，否则 MySQL 会退化为字符串比较、`idx_create_time` / `idx_finish_time` 失效。

```xml
<!-- 1) 报修类型分布：直接用工单冗余快照 fault_category，不再 join 字典表 -->
<select id="typeDistribution" resultType="map">
  SELECT o.fault_category AS category, COUNT(1) AS cnt
    FROM t_work_order o
   WHERE o.deleted = 0
     AND o.create_time &gt;= #{beginTime} AND o.create_time &lt; #{endTime}
     <if test="buildingId != null"> AND o.building_id = #{buildingId} </if>
   GROUP BY o.fault_category
</select>

<!-- 2) 按天平均处理时长：只统计已完工（CONFIRMED/CLOSED） -->
<select id="avgDuration" resultType="map">
  SELECT DATE(o.finish_time) AS d,
         ROUND(AVG(TIMESTAMPDIFF(MINUTE, o.create_time, o.finish_time))) AS avgMinutes,
         COUNT(1) AS orderCount
    FROM t_work_order o
   WHERE o.deleted = 0
     AND o.status IN ('CONFIRMED','CLOSED')
     AND o.finish_time IS NOT NULL
     AND o.finish_time &gt;= #{beginTime} AND o.finish_time &lt; #{endTime}
     <if test="buildingId != null"> AND o.building_id = #{buildingId} </if>
   GROUP BY DATE(o.finish_time)
   ORDER BY d
</select>

<!-- 3) 返修率分母：区间内完工工单数 -->
<select id="finishedCount" resultType="int">
  SELECT COUNT(1) FROM t_work_order
   WHERE deleted = 0 AND status IN ('CONFIRMED','CLOSED')
     AND finish_time &gt;= #{beginTime} AND finish_time &lt; #{endTime}
     <if test="buildingId != null"> AND building_id = #{buildingId} </if>
</select>

<!-- 4) 返修率分子：与分母同一批"区间内完工"工单中的返修单 -->
<select id="reworkCount" resultType="int">
  SELECT COUNT(1) FROM t_work_order
   WHERE deleted = 0 AND is_rework = 1 AND status IN ('CONFIRMED','CLOSED')
     AND finish_time &gt;= #{beginTime} AND finish_time &lt; #{endTime}
     <if test="buildingId != null"> AND building_id = #{buildingId} </if>
</select>

<!-- 5) 返修房间 Top10（返修率页下方表格用，口径与分子一致） -->
<select id="reworkTopRooms" resultType="map">
  SELECT b.name AS buildingName, o.room_no AS roomNo, COUNT(1) AS reworkCount
    FROM t_work_order o
    JOIN t_building b ON b.id = o.building_id
   WHERE o.deleted = 0 AND o.is_rework = 1 AND o.status IN ('CONFIRMED','CLOSED')
     AND o.finish_time &gt;= #{beginTime} AND o.finish_time &lt; #{endTime}
   GROUP BY o.building_id, o.room_no
   ORDER BY reworkCount DESC
   LIMIT 10
</select>
```

> **返修率口径**（与 7.6 一致，测试用例 **TC-M-13** 校验）：分子 = 区间内**完工**且 `is_rework=1` 的工单数；分母 = 区间内完工（`CONFIRMED`/`CLOSED`）工单数，两者都按 `finish_time` 落在 `[beginTime, endTime)`。这样分子是分母的子集，比值恒 ≤100%。分母为 0 时返回 `0` 且 `finishedCount=0`，前端显示"—"，**不得抛除零异常**。

### 8.4 MyBatis-Plus 落地要求

| 项    | 要求                                                                                                          |
| ---- | ----------------------------------------------------------------------------------------------------------- |
| 分页   | 必须在 `MybatisPlusConfig` 注册 `PaginationInnerInterceptor(DbType.MYSQL)`，否则 `Page` 对象 `total` 恒为 0             |
| 逻辑删除 | 全局配置 `logic-delete-field: deleted`，实体字段加 `@TableLogic`；统计 SQL 里仍显式写 `deleted = 0`（XML 不走全局配置）               |
| 自动填充 | `BaseEntity` 的 `createTime/updateTime` 由 `MybatisMetaObjectHandler` 填充；`createTime` 同时设 DB 默认值兜底            |
| 复杂查询 | 3 表以上 join / 聚合 / `GROUP BY` 一律写 XML（`resources/mapper/{模块}/XxxMapper.xml`），不在 Biz/Service 里 `selectList` 后内存聚合 |
| 参数   | 多参数用 `@Param` 或封装 Query 对象；**禁止** **`${}`** **拼接任何用户输入**                                                    |

| `ORDER_REWORK`    | 学生反馈未修好 | 原维修工 + 管理员  | 该单已生成返修单                     |

**推送链路（三层，逐层可降级）**

```
业务 Biz ──①落库 t_notice（REQUIRES_NEW）──▶ ②事务提交后 WebSocket 推送 ──▶ 前端 stores/notice.js
     │                                            │
     └──③(可选)发 RabbitMQ ──▶ 消费者异步发送（短信/邮件/大屏）──┘
```

1. **落库（必做）**：`noticeService.save(...)` 写 `t_notice`，保证离线用户下次登录能看到。通知写库使用 `REQUIRES_NEW` **独立事务**，通知失败只记 error 日志、不影响工单主事务（避免"通知表异常导致派单回滚"）。
2. **实时推送（默认开启）**：`WsPushService.push(userId, NoticeVO)`，在 `TransactionSynchronizationManager.afterCommit` 中执行。前端连 `ws://host/ws/notice?token={jwt}`。
3. **MQ（默认关闭）**：`app.mq.enabled=false`。开启后 `MessageProducer.send(OrderNoticeMessage)`，消费者幂等处理（按 `messageId` 去重），用于对接短信网关或多端大屏。**MQ 故障不得阻塞工单主流程**（发送失败只记 error 日志）。

> **安全提醒**：浏览器 WebSocket 无法自定义 Header，token 只能放 query，会被 Nginx access log 与浏览器历史记录。因此 `/ws/` location 必须 `access_log off;`（见 11.1），生产环境建议改用 `Sec-WebSocket-Protocol` 子协议或短时效一次性 ticket 换取连接。

**WebSocket 实现要点（照做）**

**前端要求**

- `src/utils/websocket.js`：单例连接、指数退避重连（1s→2s→4s→最长 30s）、心跳 `ping` 每 30s
- 断线不影响业务：页面由 `GET /notices/unread-count` 轮询兜底（30s 一次，仅在 WS 未连接时启用）

## 9. 权限、认证与安全设计

### 9.1 认证与鉴权流程（Spring Security 版，与 D-12 一致）

1. 登录成功后生成 JWT（`sub`=userId，`roles` 声明，`exp`=2h），同时写 Redis `sr:auth:token:{userId}` → token（用于"强制下线"与登录态校验）。**默认单端登录**：同一账号在新设备登录会覆盖该值，旧 token 下次请求即 401；若后续要求多端并存，改为 `sr:auth:token:{userId}:{jti}` 的 Hash/Set 结构，9.1 余下步骤与 15.5 同步调整。前端登录态存 `sessionStorage`（按标签页隔离），因此同一浏览器不同标签可分别登录**不同账号**互不影响；但同一账号跨标签/跨设备仍遵循本节的单端登录规则。
2. `JwtAuthenticationFilter extends OncePerRequestFilter` 位于 `UsernamePasswordAuthenticationFilter` 之前，每次请求做三件事，**任一失败即走** **`AuthenticationEntryPoint`** **返回 401**：
   - 取 Header `Authorization: Bearer {token}`，解析签名与 `exp`；
   - 校验 Redis 中 `sr:auth:token:{userId}` 是否等于该 token（不等说明已在别处登出/被踢）；Redis TTL 与 JWT `exp` 同为 2h，**不做滑动续期**，access token 过期后统一走 `/auth/refresh` 换新；
   - 构造 `UsernamePasswordAuthenticationToken`（`authorities = roles`，如 `ROLE_MANAGER`）放入 `SecurityContext`，并写入 `CurrentUserHolder`（ThreadLocal）。
3. `SecurityConfig` 白名单（`permitAll`）：`POST /api/v1/auth/login`、`GET /api/v1/files/**`、`/doc.html`、`/v3/api-docs/**`、`/actuator/health`；其余 `anyRequest().authenticated()`；开启 `@EnableMethodSecurity(prePostEnabled = true)` 使 `@PreAuthorize` 生效。
4. 退出登录：删 `sr:auth:token:{userId}` 与 `sr:auth:refresh:{userId}` + 清 `SecurityContext`（JWT 本身无状态，靠 Redis 实现"可强制下线"）。
5. 账号被禁用（`status=0`）：管理员操作时删该用户 `sr:auth:token:{userId}`、`sr:auth:refresh:{userId}`，其下次请求即 401。
6. **刷新 token**：`POST /auth/refresh` 校验 `sr:auth:refresh:{userId}`（TTL 7 天）与请求体 refreshToken 一致后，重新签发 access token 并覆盖 `sr:auth:token:{userId}`；refresh token 不可用于业务接口，避免 access 过期后无限续期绕过"强制下线"。
7. **认证失败与鉴权失败要分开返回**：未登录/凭证失效 → 401；已登录但角色不足 → 403（`AccessDeniedHandler`）。前端据此区分"跳登录页"与"提示无权限"。

> 三个由此产生的坑：① `CurrentUserHolder` 的 ThreadLocal **必须在** **`finally`** **里** **`remove()`**，否则线程池复用会把上一个请求的用户身份带给下一个请求（越权事故）；② `@PreAuthorize` 里角色必须带 `ROLE_` 前缀，库里存 `MANAGER` 时要在转 authorities 时补前缀；③ 白名单里漏了 `OPTIONS` 预检请求，前端跨域会 401。

### 10.2 查询参数默认值（避免前端不传导致全表扫描）

- `beginDate` 缺省 = 今天往前 29 天（共 30 天）
- `endDate` 缺省 = **明天 00:00:00**；前端传任意日期时，后端统一转为"该日期次日 00:00:00"作为 `endTime`（左闭右开，与 8.3 一致，禁止用 23:59:59）
- `buildingId` 缺省 = 管理员授权楼栋（查 `t_manager_building`）：只授权 1 栋时默认该栋，授权多栋或全部时默认不过滤；显式传值时校验其必须在授权范围内
- 时间跨度超过 365 天时返回 400（`STAT_RANGE_TOO_LARGE`），防止慢查询

```java
public TypeDistVO typeDist(LocalDate beginDate, LocalDate endDate, Long buildingId) {
    // 统一转成左闭右开的 LocalDateTime，避免字符串比较导致索引失效、避免漏掉当天最后一秒
    LocalDateTime beginTime = beginDate.atStartOfDay();
    LocalDateTime endTime = endDate.plusDays(1).atStartOfDay();
    String key = String.format("sr:stat:type:dist:%s:%s:%s", beginDate, endDate, buildingId);
    TypeDistVO cached = redis.get(key);
    if (cached != null) return cached;

    List<Map<String, Object>> rows = statMapper.typeDistribution(beginTime, endTime, buildingId);
    long total = rows.stream().mapToLong(r -> ((Number) r.get("cnt")).longValue()).sum();
    // ... 组装 items，计算 ratio，保留 3 位小数
    TypeDistVO vo = new TypeDistVO(total, items);
    redis.setex(key, 600, vo);
    return vo;
}
```

```nginx
        access_log off;
    }

    # ---------- 登录接口（严格限流，不缓存） ----------
    location = /api/v1/auth/login {
        limit_req zone=login_limit burst=5 nodelay;
        proxy_pass http://repair_backend;
        include /etc/nginx/conf.d/repair_proxy_common.conf;   # 见 11.2
    }

    # ---------- 其余 API 反向代理 ----------
    location /api/ {
        limit_req zone=api_limit burst=40 nodelay;
        proxy_pass http://repair_backend;
        include /etc/nginx/conf.d/repair_proxy_common.conf;   # 见 11.2

        # 接口不缓存，保证数据实时（未定义 proxy_cache，故不要写 proxy_cache_valid / proxy_no_cache）
        include /etc/nginx/conf.d/repair_security_headers.conf;
        add_header Cache-Control "no-store" always;
    }

    # ---------- WebSocket 实时通知（必须单独配 Upgrade） ----------
    location /ws/ {
        proxy_pass http://repair_backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;          # 缺少这两行 → 握手 400，前端一直重连
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        # 长连接：读超时需远大于心跳间隔（心跳 30s → 设 300s）
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
        # token 只能放在 query（?token=xxx），必须关闭访问日志，避免 token 落盘
        access_log off;
    }

    # ---------- 健康检查 ----------
    location = /health {
        access_log off;
        proxy_pass http://repair_backend/actuator/health;
    }

    # ---------- 错误页 ----------
    error_page 500 502 503 504 /50x.html;
    location = /50x.html { root /usr/share/nginx/html; }
}
```

### 11.2 公共代理配置 `deploy/nginx/repair_proxy_common.conf`

（被上面两个 location `include`，保证请求头与超时一致）

> **include 路径随系统不同，必须改（否则** **`nginx -t`** **直接报** **`No such file or directory`）**
>
> | 系统                | 主配置放哪                                                                         | include 写法                                                                                                  |
> | ----------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
> | Linux             | `/etc/nginx/conf.d/repair_proxy_common.conf`                                  | `include /etc/nginx/conf.d/repair_proxy_common.conf;`                                                       |
> | **Windows（本机实测）** | `D:\lim\loads\nginx-1.31.8\nginx-1.31.8\conf\conf.d\repair_proxy_common.conf` | `include D:/lim/loads/nginx-1.31.8/nginx-1.31.8/conf/conf.d/repair_proxy_common.conf;`（**必须正斜杠**，反斜杠会被当转义符） |
>
> **本机 Windows 实际落地（已配置并验证通过）**：Nginx 装在 `D:\lim\loads\nginx-1.31.8\nginx-1.31.8`（官方压缩包解压后会多套一层同名目录），`conf\` 下**默认没有** **`conf.d`**，需自行新建；两份配置直接放 `conf\conf.d\`，再在主配置 `conf\nginx.conf` 的 `http{ }` 块内加一行：
>
> ```nginx
> include D:/lim/loads/nginx-1.31.8/nginx-1.31.8/conf/conf.d/*.conf;
> ```
>
> 实测：**绝对路径 + 通配符**能正常解析，且不受启动目录影响。若只写相对路径 `include conf.d/*.conf;`，nginx 按**启动前缀/当前工作目录**去找，从别的目录执行会报 `No such file or directory`（见 11.6 的 `-p` 坑）。

```nginx

proxy_set_header Connection "";
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_set_header X-Request-Id $request_id;

proxy_read_timeout    60s;

proxy_next_upstream error timeout http_502 http_503;
```

### 11.2.1 安全响应头 `deploy/nginx/repair_security_headers.conf`

Nginx 的 `add_header` 是**覆盖式继承**：只要某个 `location` 里写了任意一条 `add_header`，server 级的安全头在该 location 就全部失效。因此把三条安全头抽成独立文件，在**所有写了 `add_header` 的 location** 里 `include`（11.1 中 `location /`、静态资源、图片、`/api/` 四处已接入）。

```nginx
add_header X-Frame-Options SAMEORIGIN always;
add_header X-Content-Type-Options nosniff always;
add_header Referrer-Policy no-referrer-when-downgrade always;
```

1. **`-p`** **前缀**：直接 `& "D:\...\nginx.exe" -t` 会报

### 12.8 配置绑定类 `AppProperties`（禁止满屏 `@Value`）

```java
@Data
@Component
@ConfigurationProperties(prefix = "repair")     // 与 application.yml 的 repair: 段一一对应
public class AppProperties {

    private Jwt jwt = new Jwt();
    private Upload upload = new Upload();
    private Order order = new Order();
    private Notice notice = new Notice();
    private Mq mq = new Mq();
    private Async async = new Async();

    @Data public static class Jwt {
        private String secret;
        private long expireSeconds = 7200;
        private String header = "Authorization";
        private String prefix = "Bearer ";
    }
    @Data public static class Upload {
        private int maxCountPerType = 6;      // BEFORE / AFTER 各自上限
        private int maxCountPerOrder = 12;    // 单工单总量上限（BR-13）
        private String[] allowExt = {"jpg","jpeg","png","webp"};
        private long maxSize = 5 * 1024 * 1024;
    }
    @Data public static class Order {
        private String noPrefix = "WR";
        private int autoConfirmDays = 7;      // FINISHED 满 7 天自动确认
        private int autoCloseDays = 7;        // CONFIRMED 满 7 天自动关闭
        private Map<Integer, Integer> priorityHours = new LinkedHashMap<>();
    }
    @Data public static class Notice {
        private Ws websocket = new Ws();
        @Data public static class Ws {
            private boolean enabled = true;
            private int heartbeatSeconds = 30;
            private int maxSessionsPerUser = 3;
        }
    }
    @Data public static class Mq { private boolean enabled = false; }
    @Data public static class Async {
        private int corePoolSize = 4;
        private int maxPoolSize = 8;
        private int queueCapacity = 200;
        private int keepAliveSeconds = 60;
    }
}
```

使用方式（Service 里注入，而非 `@Value("${repair.jwt.secret}")`）：

```java
@Service
@RequiredArgsConstructor
public class JwtServiceImpl {
    private final AppProperties props;            // 一处注入，全量可读
    public long expireSeconds() { return props.getJwt().getExpireSeconds(); }
}
```

> **好处与踩点**：① 改配置只改 yml，不改散落各处的注解；② `Map<Integer,Integer> priorityHours` 能直接接住 yml 的 `1: 4` 写法，取 `props.getOrder().getPriorityHours().get(priority)` 即得小时数；③ 需加 `@EnableConfigurationProperties(AppProperties.class)`（Boot 3 若未用 `@Component` 则必须显式开）；④ **不要在** **`@PostConstruct`** **里读配置再缓存成静态变量**，会与配置刷新脱节。

### 15.4 错误码表（`ResultCode`）

**编码规则**：通用错误直接用 3 位 HTTP 码；需要区分的业务错误用 5 位码，**前 3 位一般 = HTTP 状态、后 2 位 = 业务细分**。有两个**有意例外**：`40903 DUPLICATE_SUBMIT` 返回 HTTP 429（防抖限流语义）、`40905 ALREADY_MARKED_TIMEOUT` 返回 HTTP 200（幂等成功语义）。响应体中 `code` 为业务码，**HTTP 状态一律以表中 HTTP 列为准**；前端分流以 **HTTP 401/403** 为准，其余按 `code` 给提示。

| code  | 常量                           | 消息             | HTTP |
